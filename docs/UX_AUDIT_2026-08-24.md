# AyurPass Product, UX, and Reliability Audit

**Prepared by:** Manus AI  
**Date:** 24 August 2026  
**Scope:** Marketplace website, consumer and provider web workspaces, native mobile navigation, shared frontend components, and build/test health.

## Executive assessment

AyurPass already has a strong product foundation. It is not merely a wellness directory: it combines a consumer discovery and booking marketplace with provider operations, commerce, loyalty, privacy/consent controls, wellness passes, and a native mobile app. The visual system is distinctive and consistent, with a credible premium wellness direction built around forest green, warm neutrals, editorial display type, and soft illustrative cards.

The greatest product opportunity is not feature expansion. The application already contains a large feature surface. The immediate opportunity is to make the existing value easier to understand, easier to enter, and easier to operate through clearer discovery, less repetitive navigation, progressive disclosure of secondary tools, and reliable local/integration environments.

| Area | Assessment | Priority |
|---|---|---:|
| Product scope | Strong and unusually complete marketplace plus provider operating system | High opportunity |
| Visual design | Cohesive, premium, and differentiated | Preserve |
| Public discovery | Good entry proposition, but too many competing paths and repeated calls to action | High |
| Signed-in navigation | Rich but can overwhelm, especially for providers | High |
| Mobile navigation | Four tabs are purposeful; bookings and calendar are distinct list and planning workflows | Preserve |
| Engineering baseline | Type-safe and production-buildable after Prisma generation | High |
| Integration readiness | Local directory and analytics depend on external environment configuration | High |
| Dependency hygiene | `npm ci` reported 27 vulnerabilities, including 17 high severity | High |

## What was audited

The review covered the public marketplace homepage, shared navigation, installation prompt, consumer dashboard shell, provider and administrator navigation architecture, mobile tab layout, backend Prisma generation, workspace type checks, API tests, and a production Next.js build.

The primary product model observed is coherent: seekers can browse, complete a dosha assessment, book and pay for services, follow providers, manage privacy and rewards, and retain a persistent wellness pass. Providers can operate listings, bookings, staff, rooms, services, inventory, enquiries, payments, credentials, and client records. This is a powerful proposition, but it needs task-focused onboarding and navigation so users experience the value progressively rather than facing the full operational surface at once.

## Issues found and improvements implemented

### 1. Header search was not a working discovery action

The public header contained a visually polished search input and a keyboard hint, but the input did not submit a query. This created a mismatch between the interface promise and the actual experience, especially because the main public value proposition is discovery.

The shared navigation now treats this control as a real search form. It manages query state, submits to the directory through `/discover?q=…`, supports an empty query as a direct path to discovery, uses an appropriate search input type and label, and supports both `⌘K` and `Ctrl+K` focus shortcuts.

| Change | User impact | Implementation |
|---|---|---|
| Functional header search | A user can move from any public page directly into relevant discovery results | `apps/dashboard/src/components/Navbar.tsx` |
| Keyboard shortcut | Faster search for desktop users and consistency with the displayed shortcut hint | `apps/dashboard/src/components/Navbar.tsx` |
| Search semantics | Improved accessibility and browser affordances | `apps/dashboard/src/components/Navbar.tsx` |

### 2. The PWA installation prompt interrupted early discovery

The installation panel automatically appeared shortly after page load or once the browser offered installation. This competes with the homepage’s most important first-visit activity: searching for a suitable practice, service, or retreat. The panel also had an iOS completion-state issue: after viewing instructions, the button label changed to “Got it” but did not dismiss the panel.

The prompt is now strictly user-initiated through existing “Get App” and “Add to Home Screen” controls. The iOS instruction flow now dismisses correctly when the user confirms they understand the instructions. This preserves the PWA feature without making it a barrier to discovery.

| Change | User impact | Implementation |
|---|---|---|
| Removed automatic installation opening | Visitors can complete their first discovery task without an interruption | `apps/dashboard/src/components/InstallPrompt.tsx` |
| Corrected iOS “Got it” action | Users no longer remain trapped in the instruction state | `apps/dashboard/src/components/InstallPrompt.tsx` |
| Preserved user-initiated install affordances | Users can still install whenever they choose | `apps/dashboard/src/components/InstallPrompt.tsx` |

### 3. Header density was too high at medium desktop widths

At medium desktop sizes, the full navigation, quick search, country selector, account actions, and calls to action were shown simultaneously. The result was cramped and made it difficult to identify the primary task.

The wide desktop header now activates at the `xl` breakpoint. At smaller desktop and tablet widths, the app uses the existing compact menu pattern instead. This gives each control sufficient room and creates a clearer responsive hierarchy without removing any destination.

| Change | User impact | Implementation |
|---|---|---|
| Wide-navigation breakpoint shifted from `lg` to `xl` | Less crowding and better touch targets on medium desktops and tablets | `apps/dashboard/src/components/Navbar.tsx` |
| Existing menu used at compact widths | No loss of navigational coverage | `apps/dashboard/src/components/Navbar.tsx` |

### 4. Consumer dashboard had duplicate booking destinations

The consumer workspace presented both “Calendar” and “My Bookings” for the same route, making users choose between two labels for one task. This is a small issue, but it increases mental load in a product already rich in modules.

The duplicate link was removed, and the remaining link was renamed “Bookings” with an explicit hint that it contains sessions, payments, and calendar access.

| Change | User impact | Implementation |
|---|---|---|
| Removed duplicate dashboard link | One clear destination for booking management | `apps/dashboard/src/app/dashboard/layout.tsx` |
| Clarified remaining destination | Users know where sessions, payments, and calendar information live | `apps/dashboard/src/app/dashboard/layout.tsx` |

## Remaining issues and recommended next work

The following items were identified but deliberately not changed automatically because they require product, security, or deployment decisions rather than a safe UI-only patch.

| Priority | Recommendation | Why it matters | Suggested next step |
|---|---|---|---|
| P0 | Establish a dependable local integration profile | Local discovery could not load because the dashboard was not connected to a running API and dataset | Add an explicit `local` compose/dev command that starts API, PostgreSQL/PostGIS, dashboard, and deterministic seed data together |
| P0 | Remediate dependency vulnerabilities in a controlled branch | Dependency install reported 27 vulnerabilities, including 17 high severity | Run `npm audit` per workspace, review advisories and transitive paths, upgrade deliberately, and rerun API/payment regression tests |
| P0 | Make analytics and engagement integrations resilient by environment | Local browser console reported unavailable Amplitude remote config and engagement SDK loading failures | Disable these integrations cleanly in local development when keys/config are absent; avoid noisy retry loops |
| P1 | Introduce task-oriented provider navigation | Provider tools are powerful but the first-level menu is dense for an owner who wants to complete daily operations | Keep overview, schedule, clients, catalogue, and business profile prominent; move integrations, terminal, advanced staff controls, and configuration into an “Operations” or “More” group |
| P1 | Simplify homepage conversion hierarchy | The homepage repeats many destinations across the hero, feature cards, disciplines, process, pricing, and final CTA | Choose one primary seeker CTA and one provider CTA per viewport; retain discovery paths but reduce repetition and scroll length |
| P1 | Add real user-journey monitoring | Important paths span registration, quiz, discovery, booking, payment, provider onboarding, and check-in | Instrument success/failure events and define conversion funnels for seeker and provider tasks |

## Product direction

AyurPass should position its experience around two simple promises.

> **For seekers:** “Find wellness care that fits you, then manage it in one trusted place.”

> **For providers:** “Get discovered first, then activate booking, team operations, and payments when your practice is ready.”

The product should surface these promises through progressively disclosed workflows. A seeker should first see location and intention-based discovery, then personalisation through the optional dosha assessment, then booking confidence through clear credentials and privacy context. A provider should first create an attractive public profile, then receive enquiries, then activate bookable sessions, and finally expand into calendar, rooms, team, payments, CRM, and commerce as their operational maturity increases.
